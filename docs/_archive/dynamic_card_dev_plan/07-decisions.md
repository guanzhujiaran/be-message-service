## 七、技术方案决策记录

以下为已确认的技术决策，开发过程中不得擅自偏离：

| # | 议题 | 决策 | 说明 |
|---|---|---|---|
| 1 | Moment ID 生成方案 | 使用现有 `UidGenerator`(雪花) | 与用户表一致 |
| 2 | Moment正文存储方式 | JSON 全量存富文本节点（MySQL `sa.JSON()`） | 对齐 B站 Opus/Paragraph 结构 |
| 3 | Feed 流排序 | 纯按 pubTime DESC（时间倒序） | MVP 简单优先，后续加推荐算法 |
| 4 | 浏览计数粒度与触发方式 | 同用户同日同Moment只计 1 次；**由后端在动态详情接口（`GET /detail/{id}`）被真实访问时自动累计，仅登录用户计数**；**移除前端主动上报入口（`POST /view`）** | 前端不可信（用户可伪造调用上报接口虚增浏览）；后端在详情读取时按 `x-bili-mid` 识别登录用户自动 `report_view`（去重 `mid+dynId+refDate`），未登录访问不计 |
| 5 | 评论区复用 | 复用现有评论系统（CommentTypeEnum.DYNAMIC，oid=dynId） | 无重复建设，审核/封禁逻辑通用 |
| 6 | 事件提醒复用 | 复用现有 EventTypeEnum（LIKE/REPLY/AT/AUDIT_REJECT），SourceType=DYNAMIC | 联动消息中心，用户体验一致 |
| 7 | 发布Moment经验值 | **不加** | 后续迭代再考虑 |
| 8 | MVP 裁剪范围 | Phase1-4 先上线（发布+Feed+互动+统计），Phase5-7 迭代 | 尽早闭环，快速验证 |
| 9 | 审核流触发方式 | 发布后全量进入审核（严格模式） | 所有Moment必须经过审核 |
| 10 | 计数策略（likeCount/repostCount/viewCount 等） | **明细表唯一约束幂等 + 计数原子 UPDATE ±1**（主路径）+ 夜间 COUNT 对账补偿 | 计数直接存数字字段，审核状态/删除等在代码层做 ±1；点赞需同时存明细表记录谁赞了哪条Moment |
| 11 | MVP Moment 类型范围 | 仅 WORD + FORWARD（无图片上传，正文外链图） | 图片仅限正文外链 URL，视频/图文均延期 |
| 12 | 业务概念命名 | 统一命名为 **Moment（瞬间，类似知乎 Moment）**，与 B 站「动态」区分 | 表名 `TMoment*` / 模型 `TMoment*` / 枚举 `Moment*Enum` / 配置 `moment_id_*` / 路径 `/api/v1/moment`；保留列名 `dynId` 等及共享存量枚举 `SourceTypeEnum.DYNAMIC`/`CommentTypeEnum.DYNAMIC` 不变 |
| 13 | 评论举报 | 新增 `TCommentReport` 举报表（**唯一约束 `rpid + reportMid`，一人一条去重**）；举报原因复用 `MomentReportReasonEnum`（通用举报原因）；举报数达阈值时 `CommentIndex.state` 由 `normal` → `auditing`（进入审核，仅作者可见） | 对齐 B 站评论举报；复用现有举报模式（`TMomentReport` 思路）与审核状态机；**不直接改变可见性为删除**，而是转审核由管理员复核 |
| 14 | 评论举报阈值 | 可配置 `comment_report_threshold`（settings，默认 3），举报数 ≥ 阈值即转审核 | 便于运维调整；阈值指该评论累计的有效（去重后）举报记录数 |
| 15 | 动态收藏夹 | 一个用户多个收藏夹；每用户有一个**默认收藏夹**（首次进入收藏时 `get_or_create` 自动建）；收藏夹可自定义封面（**仅存 URL**）、名称、描述；收藏明细 `TMomentFavorite` 唯一约束 `dynId+folderId` 防重复；`TMomentStat.favoriteCount` 收藏/取消时原子 ±1 | 对齐 B 站收藏；封面只存链接（不转存图片）；默认收藏夹保证新用户无需先建夹即可收藏 |
| 16 | 主页收藏可见性 | 用户主页「设置」tab 内提供「是否显示收藏」开关（**默认显示**）；关闭后主页不展示「收藏」tab（对访客也不展示） | 隐私控制；开关存用户级设置（每用户一行，`get_or_create` 范式） |
| 17 | 他人主页收藏展示 | 访客可查看**他人**主页「收藏」tab（展示主人公开的收藏夹与动态）；仅当主人 `showFavorites=1` 时可见，`=0` 时访客不展示该 tab | 新增公开读接口 `GET /favorite/user/folders?mid=` / `GET /favorite/user/dynamics?mid=&folderId=`（无需登录，受主人 `showFavorites` 控制）；写入仍仅本人可操作 |
| 18 | 用户不存在错误响应 | **新增专用错误码 `USER_NOT_FOUND`**（如 `1008`），`GET /user/space/info` 目标用户不存在时返回 `code=USER_NOT_FOUND` + `msg=用户不存在` | 不再回退为空列表 / `0` / 通用 `404` 兜底，前端可精确区分「用户不存在」与其它失败 |
| 19 | 黑名单空间访问拒绝 | **前后端黑名单互访空间拒绝**：后端空间读接口（`/space/info`、`feed/space/{mid}`、`upstat`、`follow/stat`）对与目标存在黑名单关系（`i_blocked` 或 `blocked_by`，`FollowService.get_relation` 判定）的请求返回 `403` + 明确 msg；前端空间页据 `/message/follow/relation` 的 `i_blocked`/`blocked_by` 做访问拦截与受限提示 | 复用已有黑名单实现（`msg_user_follow` + `FollowStatusEnum.BLOCKED`），不新增表；保证黑名单用户在前后端均无法互访空间 |
| 20 | 空间资料字段映射 | `GET /user/space/info` 返回字段对标 B 站 acc/info；有数据源字段映射 pptr 四表（mid/name/sex/face/sign/level/birthday/vip），`is_followed` 来自关注关系；`official`/`pendant`/`nameplate`/`top_photo` 等 pptr 无数据源字段返回空结构/`null` | 不做冗余存储；缺失字段置空，前端按空态兜底展示 |
| 21 | 注销实现方式 | **分领域删除服务 + MQ 异步编排**：① 各业务「按 uid 彻底清除」拆分为独立可复用领域服务（`app/services/cleanup/` 下 `cleanup_moment`/`cleanup_comment`/`cleanup_follow`/`cleanup_report`/`cleanup_favorite`/`cleanup_dm`/`cleanup_notify`/`cleanup_event`/`cleanup_misc`/`cleanup_pptr`，各自 `delete_all_by_uid(session, uid)`）；② `UserDeactivateService` 降级为编排器，按依赖顺序（pptr 先、be-message 后）串行调用各领域服务，幂等；③ 注销接口只校验 + 投递 MQ（`message.user.deactivate` 队列），真实删除由消费者异步执行（MANUAL ack，失败不 requeue 转死信） | 拆分使各业务删除可复用/可单测，逻辑内聚于领域模块；MQ 异步避免接口同步阻塞删除大用户数据的耗时（对标 B 站注销为异步后台清理）；删除顺序/级联说明内聚到各 cleanup 服务 docstring |
| 22 | 社区互动归属 | **点赞/收藏明细与计数存 be-message，举报归属各业务系统，通用逻辑收口 bili-common**：① 点赞/收藏明细（`TMomentLike`/`TMomentFavorite`）与计数（`TInteractionStat`）统一存 be-message，`InteractionBizTypeEnum`（含 `rpa_plugin`）/ `InteractionStatBase` / `InteractionStatService` / `InteractionResourceValidator` / `StrEnum` 等通用枚举、表基类、计数逻辑收口到 bili-common 共享，各服务统一读取避免重复实现；② **举报保持归属各业务系统**：动态/评论/用户举报在 be-message，RPA 资源举报保留在 RPA-Browser（`resourcereport` + `/community/*/report` + 管理端 `/reports/*`），通用举报逻辑（幂等写/列表/审核）复用 bili-common `ReportBaseService`；③ **RPA-Browser 移除社区点赞**（删除 `resourcelike` 表与 `/community/*/like` 接口），RPA 资源点赞/收藏统一走 be-message | 单一数据源避免多服务点赞/收藏分叉；举报需各系统本地审核下架资源故保留各自系统；通用逻辑放 bili-common 避免重复 |
| 23 | 跨服务资源详情 | **be-message 通过 RPC 获取非动态资源详情返回**：be-message 只存互动明细 + 计数，不冗余存资源详情；当接口（如 `/interaction/status`）需返回非动态资源详情时，be-message 作为 RPC 客户端经 bili-common 统一契约调用资源归属服务（RPA-Browser 等）的 `get_resource_detail(biz_type, biz_id)` 获取详情一并返回；RPC 超时/资源不存在时降级仅返回互动态 + 计数（弱依赖） | 避免多服务冗余存储资源详情导致不一致；RPC 失败不影响互动主流程 |
| 24 | 动态 attach 卡片存储与渲染 | **attach 卡只存 `bizType`+`bizId`，装配为独立 `moduleType="additional"` 模块，读取时 RPC 实时获取详情**：① 存储复用 `TMoment.bizType`+`TMoment.bizRid` 两列（只落 bizType+bizId，**不冗余存 name/cover/jumpUrl 快照**，无表结构变更）；② 发布/编辑接口新增可选 `attach: {bizType, bizId}` 字段（对标 B 站 `CreateCommonAttachCard { type, biz_id }`），经 `InteractionResourceValidator` 校验资源存在；③ Feed/详情装配为独立 `moduleType="additional"` 模块（对标 B 站 `DynModuleType.module_additional` / `ModuleAdditional { type, rid }`），渲染于 desc 正文**下方**，非正文内联节点；④ name/cover/jumpUrl 由装配层按 `bizType` 批量 RPC 获取（lottery → `LotteryRpcClient.get_lottery_details`），弱依赖失败仅返回 bizType+bizId；⑤ 旧版正文 `RESOURCE` 节点（2.17.0-2.20.1 存量）读取时兼容解析 | 对标 B 站 proto；避免多服务/正文冗余存储资源快照导致不一致；附加卡与正文解耦，前端可在正文下方独立渲染 |
| 25 | `bizType` 存储类型 | **`InteractionBizTypeEnum` 由 StrEnum 改为 IntEnum（`DYNAMIC=1, LOTTERY=2, RPA_ACTION=3, RPA_WORKFLOW=4, RPA_BROWSER=5, RPA_PLUGIN=6`），DB 列 `bizType` 全部改 INT 存储（`TMoment.bizType` / `TMomentLike.bizType` / `TMomentFavorite.bizType` / `TInteractionStat.bizType`），缩小存储空间、利于索引**；**对外契约保持文字字符串**（`dynamic`/`lottery`/...）——API 入参收 string、出参转 string，经枚举 `from_text()` / `to_text()` 双向转换；RPC 契约（`get_resource_detail(biz_type, ...)` 等）与前端 SDK 类型不变（仍文字）；`InteractionResourceValidator` 注册表键改 `biz_type.value`；存量数据未上线直接删除（不做迁移） | IntEnum 落库 INTEGER 省空间（VARCHAR(32) → INT）；SQLModel 对 IntEnum 字段自动映射 INTEGER 列存 value；前后端各自维护文字映射，契约稳定无需改前端 |
| 26 | 浏览量统计泛化到非动态资源 | **`TInteractionStat` 新增 `viewCount` 列 + 新增通用浏览去重表 `TInteractionViewLog`（`bizType+bizId+mid+refDate` 唯一约束，对标 `TMomentViewLog`）**；`InteractionStatService` 新增 `report_view`（幂等：首次插入才给 `viewCount` +1，同日重复只累加明细行）；**统计触发点统一收敛到 `GET /moment/interaction/status`**——仅登录用户，对请求列表内每个资源按 `bizType+bizId+mid+refDate` 去重自动累计（dynamic 走 `MomentStatService.report_view` + `TMomentStat.viewCount`，非 dynamic 走 `InteractionStatService.report_view` + `TInteractionStat.viewCount`）；不提供前端主动上报接口，确保计数来自真实前端页面访问（页面会调 status 拉互动态）而非直接调 API | 复用「明细表幂等 + 计数原子 ±1」统一范式；status 接口为前端页面必调入口，可天然去重防伪造；动态浏览触发点（feed 详情）保持现状，与 status 双入口经 ViewLog 去重不重复计数 |
| 27 | 浏览统计异步 MQ 化 | **`/interaction/status` 不再同步写浏览**：改为对列表内每个资源组装 `InteractionViewPayload`（bizType/bizId/mid/refDate）经 `publish_interaction_view` 投递 `interaction.view` 队列（新增 `RK_VIEW` + durable 队列，复用 `message_exchange` TOPIC），投递失败静默（publisher 统一吞异常返回 False，不阻塞 status 响应）；**新增消费者 `handle_interaction_view`**：dynamic 走 `MomentStatService.report_view`、非 dynamic 走 `InteractionStatService.report_view`，消费失败 `nack(requeue=True)` 交给 MQ 独立重试（浏览上报幂等，重复执行无副作用）；**重试上限 3 次**——经 RabbitMQ `x-death` 消息头统计重投次数，超过 `MAX_VIEW_RETRIES=3` 记 ERROR 日志并 ack 丢弃，避免消息打转死循环；服务关停的 `CancelledError` 不 rollback/nack 直接上抛，避免关停二次异常噪音 | 浏览是低优先级高频率事件，异步化解耦：status 主链路不被 DB 写拖慢；MQ 提供独立重试机制替代 try/except 静默吞；RabbitMQ requeue 天然重试；与评论 count 削峰队列（Phase 3.6）同一范式 |
| 28 | `/interaction/status` 防乱调 | **status 接口对 `bizIds` 批量校验资源存在性**：dynamic 本地查 `TMoment`（`deletedAt IS NULL` 且 `auditStatus=normal` 才存在）；lottery 新增 `LotteryRpcClient.get_existing_lottery_ids(ids)` 批量 RPC（成功返回存在集合，**RPC 失败/未连接返回 None 表示校验不可用**→弱依赖降级放行，避免误伤正常用户）；其余未注册类型放行；**任一缺失 → 整体返回 400 并列出不存在的 bizId，不返回部分结果、不投递浏览 MQ** | status 兼作浏览统计触发点，不校验会被伪造资源 id 乱刷互动态/浏览数；批量校验一次 RPC/一条 SQL，无 N+1；RPC 弱依赖失败放行与 thumb/favorite 的 422 语义保持设计一致性（严格校验仅限已注册可校验类型） |
